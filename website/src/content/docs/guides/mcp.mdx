---
title: Protect an MCP resource
description: Configure MCP discovery, audience checks, and scope challenges.
---

Sésame supplies OAuth authentication and discovery. Your application supplies the MCP transport and handler.

## Register discovery and audience checks

[Register the OAuth and discovery routes](/guides/register-routes/), then [bind tokens to your MCP resource](/guides/resource-indicators/). Use the same resource path in `registerProtectedResource()` and the protecting guard.

For multiple MCP resources, define one guard per resource. Pass the matching guard to scope middleware, such as `middleware.scopes({ scopes: ['read'], guard: 'mcp' })`. Read token context from that same guard in your handler.

Enable `requireAudience` when clients send resource indicators. An unconfigured audience guard accepts tokens bound to other resources; a configured resource guard rejects those tokens.

## Enable client identification

[Enable Client ID Metadata Documents](/guides/client-metadata-documents/) for URL client IDs. Keep [dynamic registration](/guides/dynamic-registration/) enabled for clients that still need it. Select an unauthenticated-registration policy deliberately.

For metadata document clients, show document and callback hosts on consent. Each authorization requires consent and creates a separate grant.

## Advertise required scopes

Declare resource scopes when registering metadata. Use scope middleware or pass route scopes to `guard.authenticate({ scopes: ['read'] })` so 401 challenges advertise the needed permissions.

For a tool that needs more permissions after authentication, return a guard scope error:

```ts
if (!guard.hasScope('write')) throw guard.insufficientScopeError(['write'])
```

The 403 challenge includes the resource metadata URL and the union of granted and required scopes. A refresh cannot add permissions; the client needs a new authorization for the wider grant.

## Verify a client connection

Check discovery, an unauthenticated challenge, PKCE authorization, token audience, and a scoped handler call. Then test grant revocation and a client reconnect.

The repository's integration notes describe an MCP TypeScript SDK limitation: its 403 retry refreshes tokens before giving up, rather than automatically completing a wider authorization. For a client with that behavior, discard the saved tokens and reconnect to request wider scopes. Client retry behavior belongs to the SDK version your application uses.

Declare scopes on the resource or route so clients can request the challenge's scope list. Otherwise clients can fall back to discovery scopes, which include `offline_access` and can cause an explicit consent prompt. Refresh token issuance depends on the server grant setting, not on `offline_access`.
