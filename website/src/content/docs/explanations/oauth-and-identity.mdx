## API access and identity claims

An access token authorizes API requests. An ID token gives an OIDC relying party signed claims about a user. Sésame keeps access tokens opaque even when OIDC is active. The OAuth guard authenticates access tokens, not ID tokens.

OIDC is active only when both `jwk` and `oidcProvider` are configured. Without either value, OIDC discovery and JWKS return 404, and authorization requests with OIDC scopes fail with `invalid_scope`.

## Scope boundaries

Application scopes come from `config.scopes`. A request must satisfy server scope validation and the client's allowed scopes.

`openid`, `profile`, and `email` are recognized at runtime without declarations in `config.scopes`. `profile` and `email` require `openid` in the same request. A client still needs permission to request these OIDC scopes.

`offline_access` is a built-in scope. It does not replace the server and client `refresh_token` grant settings. Client credentials rejects this scope and all OIDC scopes.

Declaring `profile` and `email` in config also adds those names to inferred TypeScript scope types. Runtime recognition and type inference are separate concerns.

## Claims and providers

The store manages OAuth records. The user provider loads application users. Selecting the Kysely store does not define a user lookup or replace the login system.

For OIDC, Sésame calls the resolved user's optional `getOidcClaims(scopes)` method. Without that method, ID tokens contain protocol claims and UserInfo returns `sub`.

Sésame filters `sub`, `iss`, `aud`, `exp`, `iat`, `nonce`, and `at_hash` from custom claims. The protocol controls those values. Other claims depend on your mapping and the scopes you receive, so return only data permitted by the grant.

JWKS publishes public key components. The private JWK remains server configuration. A relying party verifies the ID token against the published key and its expected issuer and audience.
