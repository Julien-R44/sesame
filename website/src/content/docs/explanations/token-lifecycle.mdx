## Opaque tokens and database lookup

Sésame access and refresh tokens are opaque strings. The OAuth guard hashes a Bearer token, loads its record and grant, checks their validity, and resolves the application user.

The database stores SHA-256 hashes of tokens, codes, pending authorization tokens, and client secrets. ID tokens are signed JWTs for identity claims. Database lookup makes revocation visible to the guard, and makes API authentication depend on the store and user provider.

## One authorization, one grant

Every authorization creates a grant containing the client, user, approved scopes, expiry, and optional application context. Its codes and tokens reference that grant. Two authorizations for the same client and user create two grants, so revoking one does not disconnect the other device or context.

The server skips consent when active grants without context cover the requested scopes. Grants with context and metadata document clients never skip consent. `prompt=consent` forces consent, while `prompt=none` returns an error when interaction is needed.

A pending request holds one consent attempt, including the saved callback, scopes, PKCE challenge, resource, and nonce. Its `auth_token` selects the attempt. Approval or denial consumes the request atomically. Approval creates a grant; denial leaves existing grants unchanged.

## Refresh rotation and reuse

A successful refresh issues a new access token and refresh token and revokes the old refresh token. Refresh extends the grant's lifetime as tokens are renewed.

The default grace period is 120 seconds. A recently revoked refresh token can issue another new pair during that interval. The server does not return the same pair as the earlier response.

That window permits retries after lost responses or concurrent refresh requests. It also permits reuse of a stolen, recently revoked refresh token. Coordinate refresh requests and save each new pair together.

Outside the window, reuse deletes the replayed grant and revokes its tokens. Other grants of the same client and user remain valid. Set `refreshTokenRotationGracePeriod: 0` for strict detection, including retries after a lost response.

Exchanged authorization codes remain stored with `consumedAt`. A second exchange returns `invalid_grant` and revokes the code's grant. This also applies to concurrent exchanges: the slower request can invalidate the faster request's tokens.

## Existing tokens across an upgrade

Tokens issued before grants existed have no grant. Their next refresh adopts them into a new grant. A code issued before the upgrade creates a grant on exchange.

Replaying a refresh token rotated before the upgrade revokes only grant-less tokens for that client and user. Tokens already attached to a grant remain valid. A retry within the grace period still works and receives its own grant. This preserves retries across deployment without revoking another installation's authorization.

The [0.8 migration guide](/migrations/0-7-to-0-8/) describes the schema changes and consent reset.

## Cleanup and replay detection

Purge retains revoked refresh tokens for the configured retention period so the server can recognize replays. Revoked access tokens are removed immediately. Expired codes, tokens, and grants use the same retention cutoff; expired pending requests are removed immediately.

Deleting a grant invalidates its codes and tokens at the guard, introspection, and UserInfo endpoints. Revoking one access token does not revoke the whole grant. Revoking a refresh token does.
